Build Manual · Radxa Cubie A7Z

Offline Travel Assistant

A pocket Linux computer that listens, answers questions about 200,000 cities and translates between languages — with no internet at all. When Wi-Fi is there, it also answers anything, through Gemini. Written for someone who has never soldered.

Radxa Cubie A7Z · 1 GB or 2 GB ~690 MB peak RAM Works with no internet 6 solder joints
Part 0

What you are building

Four components on a 40-pin header. Six wires each for audio in and out. Everything else is software on the SD card.

INMP441 mic→ I²S in → Radxa Cubie A7Z→ I²S out → MAX98357A → speaker
on the microSD card: Vosk — hears you SQLite — 200k cities Argos — translates Piper — speaks
when Wi-Fi is available: Gemini — answers anything else

The important design decision: the offline path is the one that always runs. Gemini is an upgrade that gets first refusal when it is reachable, and everything it cannot answer falls straight through to the models on the card. The robot never goes quiet because the internet did.

Why this board and not a microcontroller

Offline speech recognition, translation and speech synthesis need roughly 690 MB of memory between them. A microcontroller like an ESP32 has about 8 MB, so everything it does must go to the cloud. The Cubie runs real Linux with 1–2 GB, which is what makes the offline half possible at all.

Part 2

Electricity, in five minutes

Enough to wire this safely.

Voltage (volts) is pressure, current (amps) is flow. Each part wants a particular voltage — here, 3.3 V or 5 V — and draws whatever current it needs. Ground (GND, the minus side) is the return path.

Rule 1 — common ground

Every part's GND connects to the board's GND. Miss this and nothing works, with no error and no smoke — signals between two parts that do not share a ground are meaningless. It is the single most common beginner fault.

Rule 2 — 3.3 V is not 5 V

The Cubie's GPIO pins run at 3.3 V. Putting 5 V into one damages it permanently. The microphone runs from 3.3 V. The amplifier can take 5 V for more volume, but then its data pins still only ever see 3.3 V signals from the board — which is fine, and is how the MAX98357A is designed to be used.

I²S
A three-wire way of moving digital audio: a clock, a left/right selector, and the data itself.
BCLK
Bit clock. Ticks once per bit of audio.
LRCLK
Left/right clock, sometimes called WS or FS. Says which channel the current sample belongs to.
GPIO
A pin you can control from software.
Part 3

The wiring

The microphone and the amplifier share one I²S bus. Only the data lines are separate.

This surprises people: you do not need two audio buses. The clock lines (BCLK and LRCLK) are shared by both devices. The microphone sends data in on one wire, the board sends data out to the amplifier on another. That is ordinary full-duplex I²S, and it is why both can run at once.

Pins 1, 2, 4, 17 (power) and every ground above are fixed by the 40-pin standard and are safe. The four I²S pins are marked with a question mark because I have not verified them on a Cubie A7Z — they are the positions most 40-pin boards use for HAT compatibility, not a fact I have checked on your board.

Confirm them yourself before soldering: run gpioinfo on the board and check Radxa's official pinout page for the A7Z. Five minutes there saves a dead board.

The two pins that produce silence rather than an error

INMP441 L/R selects which half of the audio frame the microphone speaks in. Left floating you get a stream of zeros and no error message. Tie it to GND.

MAX98357A SD is a mode select despite the name. Floating means the amplifier is off. A resistor to GND picks left, right, or the average of both — for a mono robot, use the mono setting from the module's datasheet.

Part 4

The card

Flash a headless Linux image — Armbian or Radxa OS, no desktop. A desktop eats 300–400 MB of the memory the models need.

  1. Flash the image with Balena Etcher or Raspberry Pi Imager. Put your Wi-Fi details and SSH key in during imaging if the tool offers it.
  2. Boot and connect over SSH. There is no screen on this robot, so this is how you will work from now on.
  3. Enable I²S. On Radxa OS run sudo rsetup and turn on the I²S overlay; on plain Armbian, edit /boot/armbianEnv.txt. Overlay names differ between images, so list what yours actually has rather than copying a name from a forum post for another board.
  4. Reboot, then check that arecord -l lists the microphone and aplay -l lists the amplifier.
Checkpoint

Record and play back five seconds:

arecord -D default -f S16_LE -r 16000 -c 1 -d 5 /tmp/t.wav && aplay /tmp/t.wav

If that round trip does not work, no amount of Python will help. Fix it here.

What ends up on the card

One correction to the file names

Piper voices cannot be called en_US.onnx and es_ES.onnx. Real voice files encode a full locale and a quality tier — es_ES-davefx-medium.onnx — and each needs its .onnx.json sidecar beside it, because that file holds the sample rate. Guess the rate and the voice plays at the wrong pitch and speed.

Part 5

Installing the software

  1. System packages.
    sudo apt install -y python3-venv python3-dev portaudio19-dev python3-libgpiod alsa-utils
  2. Clone and set up.
    git clone …/walle-robot-assistant ~/travel_assistant && cd ~/travel_assistant
    python3 -m venv .venv && source .venv/bin/activate
    pip install --no-cache-dir -r requirements.txt
  3. Fetch the models. ./scripts/fetch_models.sh pulls the Vosk model, the Piper binary for your architecture, and the English and Spanish voices.
  4. Install language packs. Each Argos pair is a separate ~100 MB download, so install only the ones you will use. Instructions are in docs/setup.md.
  5. Build the city database on a laptop, not the board. Indexing 200,000 rows on an SD card is painfully slow; the finished 50 MB file copies over in seconds.
    python3 scripts/build_city_db.py cities500.txt --countries countryInfo.txt --admin1 admin1CodesASCII.txt --aliases
  6. Configure. cp config.example.toml config.toml, then set your audio device and languages.
Checkpoint

Test the whole brain with no microphone involved:

python3 main_assistant.py --text "tell me about tokyo" "translate from english to spanish" "where is the station"

It prints what it would say. If the city answer and the translation are right here, the only thing left to get working is audio.

Part 6

The online half

Optional, and the robot is complete without it. With a free Gemini key it answers open questions like a phone assistant; without one it stays a city and translation device.

  1. Get a free key from Google AI Studio.
  2. export GEMINI_API_KEY=your-key-here, or put it in /etc/walle.env for the boot service.
  3. Check the startup log. online backend: Gemini means hybrid; no API key … running offline-only means local only.

The key is read from the environment and never from config.toml, so it cannot be committed to git along with your pin numbers.

What happens when the internet is flaky

A timeout, a dropped connection, a rate limit or a bad key all produce a local answer instead. A rate limit additionally stops it calling out for a minute rather than retrying into the limit. The only thing you notice is a less detailed answer.

Part 7

Talking to it

It starts in city mode and switches when you tell it to, in plain speech.

Cities — always offline

"tell me about kyoto" · "how big is san francisco" · "where is bogota"

Multi-word names work, accents do not need to be pronounced precisely, and common alternative names resolve — "bombay" finds Mumbai.

Translation — the pair switches automatically

Ask for a pair once, in your own language. Everything you say afterwards is translated, until you change it.

"translate from english to spanish"

It replies "Translating english to spanish. Go ahead." and switches itself into translator mode. Then just talk:

"where is the train station" → "¿dónde está la estación de tren?"

Other ways to say the same thing: "switch to translator mode and speak spanish" · "speak french" · "set language to german". A one-off without changing the mode: "translate the museum is closed into italian".

Everything else

"lets talk" · "switch to city guide" · "system status" · "what can you do" · "shut down"

It tells you when it cannot

Ask for a language whose pack is not installed and it says so in English. It never speaks untranslated English through a foreign voice, which sounds like a working answer and is the worst possible failure for a translator.

Argos is the biggest single consumer and the only one you can avoid — it loads on first use, not at boot. On a 1 GB board, expect the very first translation after startup to be slow while it pages in, then fast afterwards. On 2 GB it is comfortable throughout.

These are targets, not measurements

They come from the specification, and I have not run this on a board. Measure your own with ps -o rss= -p $(pgrep -f main_assistant) before trusting them. If memory gets tight, the cheapest win is to stop pre-loading Argos at boot.

Part 9

Running at boot

  1. sudo cp systemd/walle-assistant.service /etc/systemd/system/
  2. sudo systemctl enable --now walle-assistant
  3. Watch it with journalctl -u walle-assistant -f.

The service traps shutdown properly: it rests the servos, releases the GPIO lines and closes the audio stream rather than being killed mid-sentence.

Part 10

When it does not work

SymptomLook here first
Microphone records silenceThe L/R pin is floating. Tie it to GND.
No sound at all from the speakerThe amplifier's SD pin. It is a mode select, not just shutdown — floating means off.
Neither device appears in arecord -lThe I²S overlay is not enabled, or the wrong one is.
Speech plays too fast or slowThe voice's .onnx.json sidecar is missing. It carries the sample rate.
It answers its own voiceMove the microphone away from the speaker. The mic is muted during playback, but strong acoustic coupling still gets through.
Everything is slow just after bootArgos paging in on a 1 GB board. Expected, and only happens once.
Cities not foundThe database was not built or not copied. Check world_cities.db exists and is around 50 MB.
Says it has no language packThat Argos pair is not installed. It is telling you the truth.

What is verified and what is not. The software is real and tested — 260 tests covering intent routing, city lookup, the language-pair switching, translation failure handling, the Gemini backend and its failure paths, all running with no hardware attached. None of the hardware is verified: I have no Cubie, microphone, amplifier or speaker. The four I²S pin positions in Part 3, the RAM figures in Part 8, and the overlay procedure in Part 4 are reasoned from datasheets and your specification, not measured. Check them on the bench.
